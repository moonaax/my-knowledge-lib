# 上下文工程

> 上下文工程（Context Engineering）是提示工程的自然演进，关注的是"在每一次模型调用前，如何以可复用、可度量、可演进的方式，拼装并优化输入上下文"，从而在有限的注意力预算下最大化获得期望结果的概率。

相关主题：[[2-LLM大语言模型基础]] | [[../记忆与状态管理/Agent记忆系统设计]]

---

## 一、什么是上下文工程

### 1.1 从提示工程到上下文工程

在 LLM 工程的早期阶段，提示工程（Prompt Engineering）是主要工作——关注如何编写与组织 LLM 的指令以获得更优结果。然而，随着智能体在更长时间范围内、跨多次推理轮次地工作，我们需要的不再只是"找对提示词里的句式和措辞"，而是要回答一个更宏观的问题：**什么样的上下文配置，最有可能让模型产出我们期望的行为？**

所谓"上下文"，是指在对 LLM 进行采样时所包含的那组 tokens。上下文工程的核心，是在 LLM 的固有约束之下，**优化这些 tokens 的效用**。

> 🔑 上下文工程 ≠ 提示工程。提示工程关注"如何写出有效提示"，上下文工程关注"如何策划与维护最优的信息集合"——其中不仅包含提示本身，还包含系统指令、工具定义、MCP、外部数据、消息历史等一切进入上下文窗口的信息。

一个循环运行的智能体，会不断产生下一轮推理可能相关的数据，这些信息必须被**周期性地提炼**。因此，上下文工程的核心在于从持续扩张的"候选信息宇宙"中，甄别哪些内容应当进入有限的上下文窗口。

### 1.2 上下文腐蚀（Context Rot）

尽管模型的速度越来越快、可处理的数据规模越来越大，但针堆找针（needle-in-a-haystack）类基准揭示了一个现象：**上下文腐蚀（context rot）**——随着上下文窗口中的 tokens 增加，模型从上下文中准确回忆信息的能力反而下降。

这种现象源自 LLM 的架构约束。Transformer 让每个 token 能够与上下文中的**所有** token 建立关联，理论上形成 n² 级别的两两注意力关系。随着上下文长度增长，模型对这些两两关系的建模能力会被"拉薄"，从而产生"上下文规模"与"注意力集中度"的张力。此外，模型的注意力模式来源于训练数据分布——短序列通常比长序列更常见，因此模型对"全上下文依赖"的经验更少。

> 🔑 上下文必须被视作一种**有限资源**，且具有**边际收益递减**特性。就像人类有有限的工作记忆容量一样，LLM 也有一笔"注意力预算"。每新增一个 token，都会消耗这笔预算的一部分。

位置编码插值等技术可以让模型在推理时"适配"比训练期更长的序列，但会牺牲部分对 token 位置的精确理解。总体上，这些因素形成的是一个**性能梯度**，而非"悬崖式"崩溃：模型在长上下文下依旧强大，但相较短上下文，在信息检索与长程推理上的精度会有所下降。

## 二、GSSC 流水线

GSSC（Gather-Select-Structure-Compress）是一条将上下文构建过程分解为四个清晰阶段的流水线，是上下文工程的核心实践框架。

### 2.1 Gather：多源信息汇集

第一阶段从多个来源汇集候选信息，关键在于**容错性**和**灵活性**：

- **系统指令**：标记为最高优先级，不参与评分，始终保留
- **记忆系统**：从长期记忆中检索与当前查询相关的历史信息
- **RAG 知识库**：从外部知识库检索相关文档片段
- **对话历史**：仅保留最近 N 条，避免上下文窗口被历史信息占据
- **自定义信息包**：来自 NoteTool、TerminalTool 等工具的额外信息

> 🔑 每个外部数据源的调用都应被 try-except 包裹，确保单个源的失败不会影响整体流程。

### 2.2 Select：智能信息选择

第二阶段根据**相关性**和**新近性**对候选信息进行评分和选择，是整个流水线的核心。

**评分机制**：

```
综合分数 = 相关性权重 × 相关性分数 + 新近性权重 × 新近性分数
```

- **相关性**：可使用关键词重叠（Jaccard 相似度）或向量相似度计算
- **新近性**：使用指数衰减模型，24 小时内保持高分，之后逐渐衰减

**贪心选择算法**：

1. 分离系统指令和其他信息
2. 为其他信息计算综合分数
3. 过滤低于最小相关性阈值的信息
4. 按分数降序排序
5. 从高到低填充，直到达到 token 上限

```python
# 简化示意
for score, packet in scored_packets:
    if current_tokens + packet.token_count <= available_tokens:
        selected.append(packet)
        current_tokens += packet.token_count
    else:
        break  # Token 预算已满
```

### 2.3 Structure：结构化输出

第三阶段将选中的信息组织成结构化的上下文模板。推荐的分区模板：

| 分区 | 内容 | 说明 |
|------|------|------|
| `[Role & Policies]` | 角色定位和行为准则 | 系统指令，最高优先级 |
| `[Task]` | 当前需要完成的具体任务 | 用户查询 |
| `[State]` | Agent 的当前状态和上下文信息 | 可选 |
| `[Evidence]` | 从外部知识库检索的证据 | RAG 结果，用 `---` 分隔 |
| `[Context]` | 历史对话和相关记忆 | 对话历史 + 笔记 + 记忆 |
| `[Output]` | 期望的输出格式和要求 | 固定指令 |

> 🔑 结构化的好处：可读性（人类和模型都更容易理解）、可调试性（快速定位问题区域）、可扩展性（添加新信息源只需创建新分区）。

### 2.4 Compress：兜底压缩

第四阶段对超限上下文进行压缩处理。设计原则是**保持结构完整性**：

- **分区压缩**：按分区逐步填充，完整保留尽可能多的分区
- **部分保留**：对最后一个超限分区进行截断，附加 `[... 内容已压缩 ...]` 标记
- **最低保障**：至少保留 50 tokens 的有意义内容

压缩策略的调参建议：先优化**召回**（确保不遗漏关键信息），再优化**精确度**（剔除冗余内容）。一种安全的"轻触式"压缩是对"深历史中的工具调用与结果"进行清理。

## 三、有效上下文设计

在"有限注意力预算"的约束下，优秀的上下文工程目标是：**用尽可能少、但高信号密度的 tokens，最大化获得期望结果的概率**。

### 3.1 系统提示：最小必要信息集

系统提示应追求"能完整勾勒期望行为的**最小必要信息集**"（"最小"并不等于"最短"）。

常见两极误区：

| 误区 | 表现 | 后果 |
|------|------|------|
| **过度硬编码** | 在提示中写入复杂、脆弱的 if-else 逻辑 | 长期维护成本高、易碎 |
| **过于空泛** | 只给出宏观目标与泛化指引，缺少具体信号 | 模型行为不可预测，假设了错误的"共享上下文" |

实践建议：
- 用 XML/Markdown 标签分区组织（如 `<background_information>`、`<instructions>`、`<output_format>`）
- 先用最好的模型在最小提示上试跑，再依据失败模式增补清晰的指令与示例

### 3.2 工具：最小可行工具集（MVTS）

工具定义了智能体与信息/行动空间的契约，必须促进效率：

- **职责单一**、相互低重叠，接口语义清晰
- 对**错误鲁棒**
- 入参描述明确、无歧义

> 🔑 常见失败模式是"臃肿工具集"：功能边界模糊，导致"选哪个工具"这一决策本身就含混不清。如果人类工程师都说不准用哪个工具，别指望智能体做得更好。精心甄别一个"最小可行工具集（MVTS）"往往能显著提升长期交互中的稳定性与可维护性。

### 3.3 示例：多样且典型

始终推荐提供 Few-shot 示例，但不建议把"所有边界条件"的罗列一股脑塞进提示。请精挑细选一组**多样且典型**的示例，直接画像"期望行为"。对 LLM 而言，好的示例胜过千言万语。

## 四、JIT 上下文与渐进式披露

### 4.1 从预加载到即时检索

工程实践正在从"推理前一次性检索（embedding 检索）"逐步过渡到"**及时（Just-in-time, JIT）上下文**"。后者不再预先加载所有相关数据，而是维护**轻量化引用**（文件路径、存储查询、URL 等），在运行时通过工具动态加载所需数据。

这样可让模型撰写针对性查询、缓存必要结果，并用 `head`/`tail` 之类的命令分析大体量数据——无需把整块数据一次性塞入上下文。其认知模式更贴近人类：我们不会死记硬背全部信息，而是用文件系统、收件箱、书签等外部索引按需提取。

### 4.2 渐进式披露（Progressive Disclosure）

允许智能体自主导航与检索能实现**渐进式披露**：每一步交互都会产生新的上下文，反过来指导下一步决策——文件大小暗示复杂度、命名暗示用途、时间戳暗示相关性。智能体得以按层构建理解，只在工作记忆中保留"当前必要子集"。

引用的元数据本身也能帮助精化行为：目录层级、命名约定、时间戳等都在隐含地传达"目的与时效"。例如 `tests/test_utils.py` 与 `src/core/test_utils.py` 的语义暗示就不同。

### 4.3 混合策略

在不少场景中，**混合策略**更有效：前置加载少量"高价值"上下文以保证速度，然后允许智能体按需继续自主探索。边界的选择取决于任务动态性与时效要求。

> 🔑 运行时探索往往比预计算检索更慢，并且需要有"主见"的工程设计来确保模型拥有正确的工具与启发式。如果缺少引导，智能体可能会误用工具、追逐死胡同或错过关键信息，造成上下文浪费。

## 五、长时程任务策略

长时程任务要求智能体在超出上下文窗口的长序列行动中，仍能保持连贯性、上下文一致与目标导向。指望无限增大上下文窗口并不能根治"上下文污染"与相关性退化的问题，因此需要直接面向这些约束的工程手段。

### 5.1 压缩整合（Compaction）

当对话接近上下文上限时，对其进行高保真总结，并用该摘要重启一个新的上下文窗口，以维持长程连贯性。

实践要点：
- 让模型压缩并保留**架构性决策、未解决缺陷、实现细节**
- 丢弃重复的工具输出与噪声
- 新窗口携带压缩摘要 + 最近少量高相关工件（如"最近访问的若干文件"）

### 5.2 结构化笔记（Structured Note-Taking）

智能体以固定频率将关键信息写入**上下文外的持久化存储**，在后续阶段按需拉回。

价值：以极低的上下文开销维持持久状态与依赖关系。例如维护 TODO 列表、项目 NOTES.md、关键结论/依赖/阻塞项的索引，跨数十次工具调用与多轮上下文重置仍能保持进度与一致性。

笔记分类建议：
- `task_state`：记录阶段性进展和状态
- `conclusion`：记录重要的结论和发现
- `blocker`：记录阻塞问题，优先级最高
- `action`：记录下一步行动计划
- `reference`：记录重要的参考资料

### 5.3 子代理架构（Sub-Agent Architectures）

由主代理负责高层规划与综合，多个专长子代理在"干净的上下文窗口"中各自深挖、调用工具并探索，最后仅回传**凝练摘要**（常见 1,000-2,000 tokens）。

好处：实现关注点分离。庞杂的搜索上下文留在子代理内部，主代理专注于整合与推理；适合需要并行探索的复杂研究/分析任务。

### 5.4 策略选择指南

| 策略 | 适用场景 | 核心特点 |
|------|----------|----------|
| 压缩整合 | 需要长对话连续性的任务 | 上下文的"接力" |
| 结构化笔记 | 有里程碑/阶段性成果的迭代式开发与研究 | 持久化外部记忆 |
| 子代理架构 | 复杂研究与分析，能从并行探索中获益 | 关注点分离 + 并行探索 |

## 六、分层上下文管理架构

将上述策略整合，可以形成一个**三层上下文管理架构**：

| 层级 | 组件 | 特点 | 信息类型 |
|------|------|------|----------|
| **即时访问** | 终端/文件系统工具 | 按需检索，不占持久空间 | 代码结构、日志、数据文件 |
| **会话记忆** | 记忆系统（MemoryTool） | 跨轮次保持，自动衰减 | 对话历史、关键交互 |
| **持久笔记** | 笔记工具（NoteTool） | 跨会话持久化，人工可编辑 | 任务状态、结论、阻塞项 |

三层之间的协调原则：
- **即时访问**层存放可随时重建的信息（代码、日志），无需持久化
- **会话记忆**层存放有价值的交互摘要，自动管理生命周期
- **持久笔记**层存放关键决策和状态信息，需人工或半自动维护

## 面试题精选

### 1. 什么是上下文腐蚀（Context Rot）？为什么即使模型支持 100K+ 上下文窗口，仍需谨慎管理上下文？

**答**：上下文腐蚀是指随着上下文窗口中 tokens 增加，模型准确回忆信息的能力反而下降的现象。根本原因是 Transformer 的 n² 注意力机制在长序列下会被"拉薄"，加上训练数据中短序列更常见，模型对长上下文的建模经验有限。即使窗口够大，注意力预算仍是稀缺资源——每多一个 token 都在消耗模型的"专注力"。

### 2. 上下文工程与提示工程的本质区别是什么？

**答**：提示工程关注"如何写出有效的提示词"，聚焦于单次调用的指令优化；上下文工程关注"如何策划与维护最优的信息集合"，是系统级的工程问题，涵盖系统指令、工具定义、外部数据、消息历史等一切进入上下文窗口的信息，且需要在多轮推理中持续管理上下文状态。

### 3. 请解释 GSSC 流水线的四个阶段及其核心职责。

**答**：Gather（多源汇集，从记忆、RAG、对话历史、工具输出等来源收集候选信息）、Select（智能选择，基于相关性+新近性加权评分，贪心填充 token 预算）、Structure（结构化输出，将选中信息按 Role/Task/Evidence/Context/Output 分区组织）、Compress（兜底压缩，对超限上下文进行分区截断或摘要，保持结构完整性）。

### 4. 什么是"最小可行工具集（MVTS）"？为什么臃肿工具集会导致智能体表现下降？

**答**：MVTS 是指精心甄别的、职责单一且低重叠的最精简工具集。臃肿工具集的问题在于功能边界模糊，导致"选哪个工具"这一决策本身就含混不清。LLM 在工具选择上的准确性与工具描述的清晰度和差异性直接相关，工具越多、越相似，选择错误的概率越高。如果人类工程师都说不准用哪个工具，智能体更不可能做好。

### 5. JIT（Just-in-Time）上下文与传统预加载检索相比，优势和风险分别是什么？

**答**：优势——维护轻量化引用而非全量数据，按需动态加载，减少上下文浪费，引用的元数据（路径、时间戳等）本身也携带语义信息，支持渐进式披露。风险——运行时探索比预计算检索更慢，需要引导智能体正确使用工具，否则可能误用工具、追逐死胡同或错过关键信息。实践中常采用混合策略：前置加载少量高价值上下文保证速度，再允许智能体按需探索。

### 6. 长时程任务中，压缩整合、结构化笔记、子代理架构三种策略各自适用于什么场景？

**答**：压缩整合适合需要长对话连续性的任务（如多轮对话），通过高保真总结"接力"上下文；结构化笔记适合有里程碑的迭代式开发与研究，将关键信息持久化到外部存储；子代理架构适合复杂研究与分析任务，由主代理综合、子代理在干净上下文中深挖，实现关注点分离和并行探索。

### 7. 在设计系统提示时，"过度硬编码"和"过于空泛"两个极端分别会导致什么问题？如何找到平衡？

**答**：过度硬编码（写入复杂 if-else 逻辑）导致维护成本高、提示脆弱易碎；过于空泛（只给宏观目标）导致模型行为不可预测，可能假设了错误的共享上下文。平衡方法是追求"最小必要信息集"——用 XML/Markdown 标签分区组织，先在最小提示上试跑，再依据失败模式逐步增补指令与示例，直到模型稳定产出期望行为。

### 8. 如何评估一次上下文构建的质量？可以从哪些维度衡量？

**答**：可从以下维度评估：（1）**信息密度**——有效信息占总 token 的比例；（2）**相关性**——选中信息与当前任务的匹配程度；（3）**完整性**——是否遗漏了关键信息；（4）**token 效率**——在给定预算内是否最大化了有用信息；（5）**信号噪声比**——无关信息是否被有效过滤。实践建议是记录每次上下文构建的统计信息（选中信息数量、token 使用率、各分区占比），便于 A/B 测试和持续优化。
