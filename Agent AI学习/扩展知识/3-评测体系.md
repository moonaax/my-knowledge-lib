# 评测体系

> 量化评估 AI Agent / RAG / LLM 的效果，是上线前的必经之路。没有评测 = 不知道能不能上线。
> 相关主题：[[../RAG检索增强生成/1-RAG原理与架构]] | [[../基础概念/2-LLM大语言模型基础]]

---

## 一、为什么需要评测

### 1.1 没有评测的风险

```
用户问：LCEL 是什么？
Agent 回答：LCEL 是 LangChain Expression Language（正确）
→ 看起来没问题

但换个问法：
用户问：LCEL 怎么用？
Agent 回答：LCEL 是一种编程语言（错误）
→ 不评测根本发现不了
```

**核心问题**：LLM 的输出有随机性，同样的问题不同时间可能得到不同答案。靠人工测几个 case 不够，需要系统化评测。

### 1.2 评测的三个层次

| 层次 | 评测对象 | 方法 | 成本 |
|------|---------|------|------|
| **单元评测** | 单个组件（Prompt、Retriever、Tool） | 固定输入输出对比 | 低 |
| **集成评测** | 整条链路（RAG Pipeline） | QA 对匹配 | 中 |
| **端到端评测** | 完整产品（Agent 交互） | 人工评测 / LLM-as-Judge | 高 |

## 二、LLM 评测

### 2.1 通用基准

| 基准 | 评测内容 | 特点 |
|------|---------|------|
| **MMLU** | 57 个学科的选择题 | 最通用的 LLM 评测基准 |
| **HumanEval** | 代码生成 | 164 个编程题 |
| **GSM8K** | 数学推理 | 8500 道小学数学题 |
| **MT-Bench** | 多轮对话质量 | GPT-4 打分 |
| **AlpacaEval** | 指令遵循 | 与 GPT-4 对比胜率 |
| **C-Eval** | 中文综合 | 52 个中文科目 |
| **SuperCLUE** | 中文评测 | 国内最权威的中文 LLM 评测 |

### 2.2 MT-Bench 详解（最实用）

MT-Bench 用 GPT-4 作为裁判，给模型回答打 1-10 分：

```
评分流程：
1. 准备 80 个多轮对话题（涵盖写作、推理、数学、编程等）
2. 让被测模型回答
3. GPT-4 打分（1-10 分）
4. 计算平均分

评分标准：
- 9-10：优秀，专业水准
- 7-8：良好，基本满足需求
- 5-6：一般，有明显问题
- 3-4：较差，经常出错
- 1-2：很差，基本不可用
```

**为什么用 GPT-4 打分**：人工评测成本太高（一个回答需要多人标注），GPT-4 打分与人类评分相关性 > 0.85。

### 2.3 LLM-as-Judge 模式

用一个 LLM 评测另一个 LLM 的输出：

```python
# 评测 Prompt 模板
judge_prompt = """
请评判以下回答的质量，从 1-10 打分。

问题：{question}
参考答案：{reference}
模型回答：{answer}

评分标准：
- 准确性（0-4 分）：事实是否正确
- 完整性（0-3 分）：是否涵盖了关键点
- 清晰度（0-3 分）：表达是否清楚

输出格式：
分数：X
理由：...
"""
```

**注意事项**：
- 评委模型要比被测模型强（用 GPT-4 评测 7B 模型）
- 评分有 position bias（倾向给第一个回答高分）→ 打乱顺序测两次
- 不同评委模型打分标准不同 → 固定用同一个评委

### 2.4 LLM Judge 四维度评分体系

> 🔑 LLM-as-Judge 不只是打一个总分，还可以从多个维度拆解评分，再通过及格率、优秀率等指标汇总整体质量。

在实际项目中，LLM Judge 通常从以下四个维度进行 1-5 分评分：

| 维度 | 英文名 | 评估内容 | 评分标准 |
|------|--------|---------|---------|
| **正确性** | Correctness | 逻辑是否正确，答案是否准确 | 5分：完全正确；3分：大致正确有小错；1分：根本性错误 |
| **清晰度** | Clarity | 表述是否清晰，是否易理解 | 5分：结构清晰表达精准；3分：基本可读但有模糊处；1分：混乱难懂 |
| **难度匹配** | Difficulty Match | 难度是否符合目标标准 | 5分：难度精准匹配；3分：略有偏差；1分：难度完全不匹配 |
| **完整性** | Completeness | 步骤是否完整，是否遗漏关键信息 | 5分：覆盖所有关键点；3分：有遗漏但核心完整；1分：严重缺失 |

**三个汇总指标**：

```
平均分（Average Score）= 所有样本的四个维度得分之和 / (4 × 样本数)

及格率（Pass Rate）= 平均分 ≥ 3.5 的样本数 / 总样本数
  → 衡量基本质量保障，反映"大部分样本质量达标"

优秀率（Excellent Rate）= 平均分 ≥ 4.5 的样本数 / 总样本数
  → 衡量高质量产出能力，反映"有多少样本质量优秀"
```

> 🔑 实战建议：及格率目标 ≥ 80%，优秀率目标 ≥ 30%。如果及格率低说明生成策略有系统性问题，如果及格率高但优秀率低说明质量不够精。

**代码示例**：

```python
# LLM Judge 四维度评分 Prompt 模板
judge_prompt = """
请评估以下内容的质量，从以下 4 个维度评分（1-5 分）：

1. 正确性 (Correctness)：逻辑是否正确，答案是否准确
2. 清晰度 (Clarity)：表述是否清晰，是否易理解
3. 难度匹配 (Difficulty Match)：难度是否符合目标标准
4. 完整性 (Completeness)：步骤是否完整，是否遗漏关键信息

待评估内容：
{content}

请按以下 JSON 格式输出：
{
    "correctness": 5,
    "clarity": 4,
    "difficulty_match": 4,
    "completeness": 5,
    "comments": "评价理由"
}
"""

def compute_judge_metrics(scores_list):
    """计算 LLM Judge 三个汇总指标"""
    avg_scores = [sum(s.values()) / 4 for s in scores_list]
    avg_score = sum(avg_scores) / len(avg_scores)
    pass_rate = sum(1 for s in avg_scores if s >= 3.5) / len(avg_scores)
    excellent_rate = sum(1 for s in avg_scores if s >= 4.5) / len(avg_scores)
    return {
        "avg_score": avg_score,
        "pass_rate": pass_rate,
        "excellent_rate": excellent_rate
    }
```

### 2.5 Win Rate 成对对比评估

> 🔑 Win Rate 是一种**相对评估**方法：让 LLM 同时看两个回答，判断哪个更好，统计胜率/败率/平局率。

与 LLM Judge 的绝对评分不同，Win Rate 通过**成对对比（Pairwise Comparison）**来衡量模型输出的相对质量：

```
评估流程：
1. 准备待评估输出（A）和参考输出（B）
2. 打乱 A/B 顺序（消除 position bias）
3. LLM 判断：A 更好（Win）、B 更好（Loss）、持平（Tie）
4. 统计多次对比的胜率/败率/平局率
```

**三个核心指标**：

| 指标 | 公式 | 含义 |
|------|------|------|
| **胜率 Win Rate** | Wins / Total | 待评估输出被判定为更好的比例 |
| **败率 Loss Rate** | Losses / Total | 参考输出被判定为更好的比例 |
| **平局率 Tie Rate** | Ties / Total | 两者质量相当的比例 |

> 🔑 Win Rate + Loss Rate + Tie Rate = 100%。理想结果：Win Rate ≈ 50%，说明待评估输出与参考质量相当。

**代码示例**：

```python
comparison_prompt = """
请比较以下两个回答的质量。

【回答 A】
{answer_a}

【回答 B】
{answer_b}

请从以下方面比较：
1. 逻辑的严谨性
2. 表述的清晰度
3. 内容的完整性
4. 信息的准确性

请按以下 JSON 格式输出：
{"winner": "A" 或 "B" 或 "Tie", "reason": "判断理由"}
"""

def compute_win_rate(results):
    """计算 Win Rate 三个指标"""
    total = len(results)
    wins = sum(1 for r in results if r["winner"] == "A")
    losses = sum(1 for r in results if r["winner"] == "B")
    ties = sum(1 for r in results if r["winner"] == "Tie")
    return {
        "win_rate": wins / total,
        "loss_rate": losses / total,
        "tie_rate": ties / total
    }
```

**注意事项**：
- 必须打乱 A/B 顺序测两次，取平均值，消除 position bias
- LLM Judge 和 Win Rate 可以互补使用：LLM Judge 看绝对质量，Win Rate 看相对质量
- Win Rate 最适合对比两个系统的输出，不适合评估单个系统

## 三、RAG 评测

### 3.1 RAG 评测维度

RAG 系统需要从三个维度评测：

```
                    ┌─────────────┐
                    │  最终回答质量 │
                    └──────┬──────┘
              ┌────────────┼────────────┐
              ▼            ▼            ▼
        ┌──────────┐ ┌──────────┐ ┌──────────┐
        │ 检索质量  │ │ 生成质量  │ │ 忠实度    │
        │ Retrieval│ │Generation│ │ Faithful │
        └──────────┘ └──────────┘ └──────────┘
```

| 维度 | 评测指标 | 含义 |
|------|---------|------|
| **检索质量** | Recall@K | 前 K 个结果中包含正确答案的比例 |
| **检索质量** | MRR | 第一个正确结果的排名倒数 |
| **检索质量** | NDCG | 考虑排序位置的检索质量 |
| **生成质量** | Answer Accuracy | 回答是否正确 |
| **生成质量** | Answer Completeness | 回答是否完整 |
| **忠实度** | Faithfulness | 回答是否基于检索到的内容（不幻觉） |
| **忠实度** | Relevance | 回答是否与问题相关 |

### 3.2 RAGAS 框架（最流行的 RAG 评测框架）

RAGAS（Retrieval Augmented Generation Assessment）提供四个自动评测指标：

```python
# 安装
pip install ragas

# 使用
from ragas import evaluate
from ragas.metrics import faithfulness, answer_relevancy, context_precision, context_recall

# 准备评测数据
eval_data = {
    "question": ["LCEL 是什么？"],
    "answer": ["LCEL 是 LangChain Expression Language..."],
    "contexts": [["LCEL（LangChain Expression Language）是 LangChain 的核心..."]],
    "ground_truth": ["LCEL 是 LangChain 的表达式语言，用于链式调用"]
}

# 运行评测
result = evaluate(
    dataset=eval_data,
    metrics=[faithfulness, answer_relevancy, context_precision, context_recall],
)
print(result)
```

**四个核心指标**：

| 指标 | 含义 | 计算方式 |
|------|------|---------|
| **Faithfulness** | 回答是否忠实于检索内容 | 把回答拆成句子，检查每句是否有上下文支持 |
| **Answer Relevancy** | 回答是否与问题相关 | 用 LLM 从回答反推问题，与原问题比较相似度 |
| **Context Precision** | 检索内容的精确度 | 相关文档是否排在前面 |
| **Context Recall** | 检索内容的召回率 | 参考答案中的信息是否被检索到 |

### 3.3 构建 RAG 评测集

**方法一：人工构建（最准确）**


## 四、Agent 评测

### 4.1 Agent 评测的难点

Agent 评测比 RAG 更复杂：

| 挑战 | 说明 |
|------|------|
| **多步骤** | Agent 可能调用多个工具，中间步骤也需要评测 |
| **非确定性** | 同一个问题可能有多种正确的工具调用路径 |
| **工具依赖** | 外部 API 不稳定，影响评测结果 |
| **状态管理** | 多轮对话中的状态变化需要追踪 |

### 4.2 Agent 评测维度

| 维度 | 指标 | 说明 |
|------|------|------|
| **任务完成率** | Success Rate | 最终是否完成了用户任务 |
| **工具选择准确率** | Tool Accuracy | 是否选对了工具 |
| **参数提取准确率** | Argument Accuracy | 工具参数是否正确 |
| **步骤效率** | Step Efficiency | 完成任务用了多少步（越少越好） |
| **错误恢复率** | Recovery Rate | 出错后能否自动修复 |
| **延迟** | Latency | 端到端响应时间 |

### 4.3 实战：我们的评测脚本

项目中的 `eval_rag.py` 实现了简单的 RAG 评测：

```python
# eval_rag.py 的评测逻辑
def evaluate():
    results = []
    for qa in eval_set:
        # 调用 RAG 链
        answer = rag_chain.invoke(qa["question"])
        # 关键词命中率
        keywords = qa["keywords"]
        hits = sum(1 for kw in keywords if kw in answer)
        keyword_score = hits / len(keywords)
        # 来源准确率（检查是否检索到了正确文档）
        source_score = check_sources(answer, qa["expected_source"])
        results.append({
            "question": qa["question"],
            "keyword_score": keyword_score,
            "source_score": source_score
        })
    # 汇总
    avg_keyword = sum(r["keyword_score"] for r in results) / len(results)
    avg_source = sum(r["source_score"] for r in results) / len(results)
    print(f"关键词命中率: {avg_keyword:.1%}")
    print(f"来源准确率: {avg_source:.1%}")
```

**25 个 QA 对覆盖的知识领域**：
- LangChain 基础（LCEL、Chain、Memory）
- Agent 概念（ReAct、Tool、Function Calling）
- RAG（向量检索、Embedding、Chunk）
- LangGraph（StateGraph、条件路由）
- 生产化（Docker、LangSmith、量化）

### 4.4 BFCL：工具调用能力评估基准

> 🔑 BFCL（Berkeley Function Calling Leaderboard）是 UC Berkeley 推出的函数调用评估基准，专注于衡量智能体的工具调用准确性。

#### 4.4.1 概述

BFCL 包含 1120+ 测试样本，按难度递增分为四个评估类别：

| 类别 | 说明 | 难度 |
|------|------|------|
| **Simple** | 单函数调用，基础场景 | 低 |
| **Multiple** | 需要依次调用多个函数 | 中 |
| **Parallel** | 需要并行调用多个函数 | 高 |
| **Irrelevance** | 判断是否需要调用函数（含不需要调用的场景） | 高 |

每个测试样本包含 `question`（用户请求）、`function`（可用函数列表，含签名和描述）、`ground_truth`（标准答案）。

#### 4.4.2 AST 匹配算法

> 🔑 BFCL 的核心创新是使用 **AST 匹配（Abstract Syntax Tree Matching）**，而非简单字符串匹配。AST 匹配将函数调用解析为语法树，比较树的结构和节点值。

三个匹配规则：
1. **函数名**必须精确匹配（`get_weather` ≠ `get_temperature`）
2. **参数键值对**集合相等，忽略顺序（`f(a=1, b=2)` = `f(b=2, a=1)`）
3. **参数值**语义等价（`f(x=2+3)` = `f(x=5)`，`f(s="hello")` = `f(s='hello')`）

```python
# AST 匹配示例
预测: get_weather(city="Beijing", unit="celsius")
标准: get_weather(unit="celsius", city="Beijing")
结果: ✅ 匹配成功（参数顺序不同，AST 等价）

预测: calculate(x=2+3)
标准: calculate(x=5)
结果: ✅ 匹配成功（表达式等价）

预测: get_temperature(city="Beijing")
标准: get_weather(city="Beijing")
结果: ❌ 匹配失败（函数名不同）
```

#### 4.4.3 评估指标

```python
# 核心指标：准确率（Accuracy）
Accuracy = AST匹配成功数 / 总样本数

# 分类准确率：每个类别单独计算
Accuracy_c = 该类别匹配成功数 / 该类别样本数

# 加权准确率：考虑不同类别难度
Weighted_Accuracy = Σ(w_c × Accuracy_c)
```

**实战代码**：

```python
# 使用 bfcl 官方评估工具
# pip install bfcl-eval

bfcl evaluate \
    --model-result-path ./results.json \
    --test-category simple_python
```

#### 4.4.4 评估流程

```
1. 加载 BFCL 数据集（JSON 格式，含函数定义和标准答案）
2. 将 question + function 列表构造为 prompt 发给被测 Agent
3. 从 Agent 响应中提取函数调用（支持 JSON / 代码块 / 纯文本格式）
4. 用 AST 匹配算法比较预测结果和标准答案
5. 计算准确率等指标，生成评估报告
```

> 🔑 实战建议：先从 Simple 类别开始确保基础能力，再逐步测试 Multiple、Parallel、Irrelevance。评估时使用官方工具确保结果可与排行榜对比。

### 4.5 GAIA：通用 AI 助手能力评估基准

> 🔑 GAIA（General AI Assistants）是 Meta AI 和 Hugging Face 联合推出的通用能力评估基准，包含 466 个真实世界问题，评估智能体的综合问题解决能力。

#### 4.5.1 概述

GAIA 的设计理念：真实世界的问题往往需要多种能力的综合运用。与 BFCL 专注于工具调用不同，GAIA 评估的是**多步推理 + 知识运用 + 工具使用 + 文件处理**的综合能力。

**三个难度级别**：

| 级别 | 推理步骤 | 能力要求 | 示例 |
|------|---------|---------|------|
| **Level 1** | 1-2 步 | 基础推理，可能需要一个工具 | "某城市的首都是什么？" |
| **Level 2** | 3-5 步 | 多步推理，需要多个工具 | "统计某国前3大城市的人口总和" |
| **Level 3** | 5+ 步 | 复杂推理，需要文件处理和网页浏览 | "分析给定PDF中的数据并回答问题" |

数据集包含 165 个验证集样本（Level 1: 53, Level 2: 62, Level 3: 50）和 301 个测试集样本。

#### 4.5.2 准精确匹配算法（Quasi Exact Match）

> 🔑 GAIA 使用准精确匹配算法，核心思想是**先对答案归一化处理，再做精确匹配**。

归一化规则按答案类型区分：

```python
# 数字答案：移除逗号和单位
"$1,234.56" → "1234.56"
"50%" → "50"

# 字符串答案：转小写、移除冠词、移除多余空格
"The United States" → "united states"
"the apple" → "apple"

# 列表答案：每个元素归一化后按字母排序
"Paris, London, Berlin" → "berlin, london, paris"
```

答案格式要求：必须以 `FINAL ANSWER: [答案]` 给出，数字不使用逗号分隔和单位，字符串不使用冠词和缩写。

#### 4.5.3 评估指标

```python
# 精确匹配率（核心指标）
Exact_Match_Rate = 准精确匹配成功数 / 总样本数

# 分级准确率（按难度级别）
Accuracy_ℓ = 该级别匹配成功数 / 该级别样本数

# 难度递进下降率（衡量难度增加时的性能衰减）
Drop_Rate = (Accuracy_ℓ - Accuracy_ℓ+1) / Accuracy_ℓ
# 下降率越大，说明处理复杂任务时能力衰减越明显
```

**计算示例**：

```python
# 假设评估了 10 个样本
Level 1: 3/3 = 100%
Level 2: 2/3 = 67%
Level 3: 2/4 = 50%

# 难度递进下降率
Drop(1→2) = (1.00 - 0.67) / 1.00 = 33%   # 中等难度导致 33% 衰减
Drop(2→3) = (0.67 - 0.50) / 0.67 = 25%   # 高难度导致 25% 衰减
```

## 五、评测最佳实践

### 5.1 评测流程

```
1. 构建评测集（至少 20-50 个 QA 对）
2. 跑基线（当前版本的分数）
3. 改动 Prompt / 检索策略 / 模型
4. 重新评测，对比基线
5. 回归测试（确保没引入新问题）
```

### 5.2 自动化评测 Pipeline

```python
# 评测 Pipeline
def eval_pipeline(version: str):
    # 1. 跑评测集
    results = run_eval(eval_set)
    # 2. 计算指标
    metrics = compute_metrics(results)
    # 3. 与基线对比
    baseline = load_baseline()
    diff = compare(metrics, baseline)
    # 4. 生成报告
    report = generate_report(version, metrics, diff)
    # 5. 发送到 LangSmith
    log_to_langsmith(version, metrics)
    return report
```

### 5.3 评测陷阱

| 陷阱 | 说明 | 解决方案 |
|------|------|---------|
| **评测集太小** | 5 个 case 不能代表真实场景 | 至少 20 个，覆盖不同类型 |
| **评测集泄露** | 用训练数据做评测 | 评测集必须独立于训练数据 |
| **只看平均分** | 平均分高但某个类型很差 | 分类统计，找到薄弱点 |
| **忽略边界情况** | 只测正常输入 | 加入模糊/错误/对抗性输入 |
| **评测环境不一致** | 模型版本/API 变化影响结果 | 锁定版本，记录环境信息 |

## 七、面试要点

**Q: RAG 系统怎么评测？**

从三个维度：①检索质量（Recall@K、MRR）②生成质量（Answer Accuracy）③忠实度（Faithfulness，是否幻觉）。推荐用 RAGAS 框架自动化评测，核心指标是 Faithfulness、Answer Relevancy、Context Precision、Context Recall。评测集至少 20 个 QA 对，覆盖不同类型的问题。

**Q: LLM-as-Judge 是什么？有什么问题？**

用强 LLM（如 GPT-4）给弱 LLM 的输出打分。优点是成本低、可规模化；问题是存在 bias：position bias（倾向第一个回答）、verbosity bias（倾向长回答）、self-enhancement bias（给自己打高分）。解决方法：打乱顺序测两次、用多个评委、固定评委模型。

**Q: Agent 评测和 RAG 评测有什么区别？**

RAG 评测关注检索+生成，指标相对固定。Agent 评测更复杂——需要评测多步骤的工具选择、参数提取、错误恢复能力。核心指标是任务完成率和步骤效率。Agent 评测需要模拟工具调用（mock 外部 API），否则评测结果不稳定。

**Q: 你们项目的评测是怎么做的？**

用 25 个 QA 对覆盖 LangChain/RAG/Agent 核心知识点，评测指标是关键词命中率和来源准确率。通过 eval_rag.py 自动化评测，每次改动 Prompt 或检索策略后跑一遍对比基线。生产环境接入 LangSmith 做 trace + 评测，可以追踪每次请求的完整链路。

**Q: BFCL 是什么？为什么用 AST 匹配而不是字符串匹配？**

BFCL 是 UC Berkeley 的工具调用能力评估基准，包含 Simple/Multiple/Parallel/Irrelevance 四个类别。AST 匹配比字符串匹配更智能：它将函数调用解析为抽象语法树，能忽略参数顺序（`f(a=1, b=2)` = `f(b=2, a=1)`）、识别等价表达式（`2+3` = `5`）、忽略格式差异。而字符串匹配对格式极其敏感，会把语义等价的调用判为错误。

**Q: GAIA 评估基准有什么特点？它的准精确匹配算法是怎么工作的？**

GAIA 是 Meta AI 推出的通用能力评估基准，466 个真实问题分 3 个难度级别，评估多步推理、工具使用、文件处理等综合能力。准精确匹配算法先对答案归一化：数字移除逗号和单位、字符串转小写移除冠词、列表元素排序后再精确比较。这样 `"The United States"` 和 `"united states"` 会被判定为匹配。

**Q: LLM Judge 的四维度评分体系是什么？及格率和优秀率怎么用？**

LLM Judge 从正确性、清晰度、难度匹配、完整性四个维度各打 1-5 分。及格率（平均分 ≥ 3.5 的比例）衡量基本质量保障，目标 ≥ 80%；优秀率（平均分 ≥ 4.5 的比例）衡量高质量产出能力，目标 ≥ 30%。如果及格率低说明生成策略有系统性问题，如果及格率高但优秀率低说明质量不够精。

**Q: Win Rate 评估和 LLM Judge 有什么区别？**

LLM Judge 是绝对评分（给单个回答打分），Win Rate 是相对评估（成对对比两个回答哪个更好）。Win Rate 统计胜率/败率/平局率，理想结果是 Win Rate ≈ 50%（说明与参考质量相当）。两者互补：LLM Judge 看绝对质量水平，Win Rate 看与参考的相对差距。Win Rate 需要打乱 A/B 顺序测两次消除 position bias。
