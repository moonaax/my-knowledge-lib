# 智能体通信协议

> 智能体通信协议是 AI Agent 系统的基础设施层，定义了智能体与工具、智能体与智能体之间的标准化通信方式。主流协议包括 MCP（工具访问）、A2A（智能体协作）和 ANP（大规模网络），三者分别解决不同层级的通信问题，共同构成智能体生态的通信底座。

相关主题：[[../框架与工具/1-LangChain框架详解]] | [[../框架与工具/构建自定义Agent框架]]

## 一、为什么需要通信协议

### 1.1 工具集成困境

传统的智能体工具集成方式是为每个外部服务编写专门的适配器类。例如访问 GitHub 需要写 `GitHubTool`，访问数据库需要写 `DatabaseTool`，每个工具都要独立处理 HTTP 请求、错误处理、认证逻辑等。这种方式存在四个根本问题：

- **代码重复**：每个工具都要处理相同的基础逻辑（网络请求、重试、超时等）
- **难以维护**：API 变更时需要修改所有相关工具
- **无法复用**：不同开发者编写的工具无法互相兼容
- **扩展性差**：添加新服务需要大量编码工作

### 1.2 能力扩展瓶颈

智能体的能力被限制在预先定义的工具集内，无法在运行时动态发现和使用新的服务。当面对复杂任务时，智能体无法像人类一样"找到合适的工具来完成工作"。

### 1.3 协作缺失

当任务复杂到需要多个专业智能体协作时（如研究员 + 撰写员 + 编辑），只能通过手动编排来协调它们的工作，缺乏标准化的通信机制。

> 🔑 通信协议的核心价值：提供标准化的接口规范，让智能体以统一的方式访问各种外部服务，实现互操作性、动态发现和可扩展性。就像 TCP/IP 让不同设备能相互通信一样，通信协议让智能体生态能够互联互通。

## 二、MCP（Model Context Protocol）

### 2.1 设计理念

MCP 由 Anthropic 提出，其核心设计理念是**标准化智能体与外部工具/资源的通信方式**。MCP 就像智能体的"USB-C"——无论使用 Claude、GPT 还是其他模型，只要支持 MCP 协议，就能无缝访问相同的工具和资源。

MCP 的设计哲学是"上下文共享"。它不仅仅是 RPC（远程过程调用）协议，更重要的是允许智能体和工具之间共享丰富的上下文信息。例如当智能体访问代码仓库时，MCP 服务器不仅能提供文件内容，还能提供代码结构、依赖关系、提交历史等上下文。

### 2.2 三层架构

MCP 采用 Host / Client / Server 三层架构：

| 层级 | 职责 | 示例 |
|------|------|------|
| **Host（宿主层）** | 接收用户提问，管理对话流程 | Claude Desktop、自定义应用 |
| **Client（客户端层）** | 与 MCP Server 建立连接，发送请求并接收响应 | 内置的 MCP Client |
| **Server（服务器层）** | 执行实际操作，返回结果 | 文件系统 Server、GitHub Server |

**完整交互流程**：用户问题 → Host → LLM 分析 → 需要工具 → MCP Client 连接 → MCP Server 执行 → 返回结果 → LLM 生成回答

这种架构的优势在于**关注点分离**：Host 专注于用户体验，Client 专注于协议通信，Server 专注于具体功能实现。开发者只需关注 MCP Server 的开发。

### 2.3 核心能力

MCP 提供三大核心能力：

- **Tools（工具）**：主动的，执行操作（如搜索、写文件、调用 API）
- **Resources（资源）**：被动的，提供数据（如文件内容、数据库记录）
- **Prompts（提示模板）**：指导性的，提供预定义的提示模板

### 2.4 MCP vs Function Calling

这是开发者最常问的问题。两者并非竞争关系，而是相辅相成：

| 维度 | Function Calling | MCP |
|------|-----------------|-----|
| **本质** | 模型的内在能力 | 基础设施协议 |
| **作用** | 让模型理解何时调用函数 | 定义工具如何被描述和调用 |
| **耦合度** | 与特定 LLM 提供商绑定 | 模型无关，跨平台通用 |
| **工具发现** | 需手动定义工具列表 | 运行时自动发现 |
| **代码复用** | 切换模型需重写适配器 | 一次开发，多模型通用 |

> 🔑 类比理解：Function Calling 相当于你学会了"如何打电话"这项技能（何时拨号、如何沟通、何时挂断）。MCP 则是全球统一的"电话通信标准"，确保任何一部电话都能拨通另一部。

**Function Calling 方式**（需为每个 LLM 适配）：

```python
# OpenAI 格式
openai_tools = [{"type": "function", "function": {"name": "search_github", ...}}]
# Claude 格式（注意是 input_schema 不是 parameters）
claude_tools = [{"name": "search_github", "input_schema": {...}}]
# 还需自己实现工具函数和处理不同模型的响应格式
```

**MCP 方式**（模型无关）：

```python
from hello_agents.protocols import MCPClient

# 连接到社区 MCP 服务器，无需自己实现
github_client = MCPClient(["npx", "-y", "@modelcontextprotocol/server-github"])

async with github_client:
    tools = await github_client.list_tools()       # 自动发现工具
    result = await github_client.call_tool(         # 统一调用接口
        "search_repositories", {"query": "AI agents"}
    )
# 任何支持 MCP 的模型都能使用相同的客户端
```

### 2.5 五种传输方式

MCP 协议具有**传输层无关性**，支持五种传输方式：

| 传输方式 | 适用场景 | 说明 |
|---------|---------|------|
| **Memory** | 单元测试、快速原型 | 内存传输，不涉及网络 |
| **Stdio** | 本地开发、调试 | 通过标准输入输出与本地进程通信，最常用 |
| **HTTP** | 生产环境、远程服务 | 标准 HTTP 请求/响应 |
| **SSE** | 实时通信、流式处理 | Server-Sent Events，支持服务端推送 |
| **StreamableHTTP** | 双向流式通信 | 结合 HTTP 和流式传输的优势 |

### 2.6 自定义 MCP 服务器开发

构建自定义 MCP 服务器的主要动机：封装业务逻辑、访问私有数据、性能优化、功能定制。

以下是天气查询 MCP 服务器的核心实现：

```python
from hello_agents.protocols import MCPServer
import json, requests

# 创建 MCP 服务器
weather_server = MCPServer(name="weather-server", description="天气查询服务")

def get_weather(city: str) -> str:
    """获取指定城市的当前天气"""
    url = f"https://wttr.in/{city}?format=j1"
    response = requests.get(url, timeout=10)
    data = response.json()
    current = data["current_condition"][0]
    result = {
        "city": city,
        "temperature": float(current["temp_C"]),
        "humidity": int(current["humidity"]),
        "condition": current["weatherDesc"][0]["value"],
    }
    return json.dumps(result, ensure_ascii=False)

def list_supported_cities() -> str:
    """列出所有支持的城市"""
    cities = ["北京", "上海", "广州", "深圳", "杭州", "成都"]
    return json.dumps({"cities": cities, "count": len(cities)})

# 注册工具到服务器
weather_server.add_tool(get_weather)
weather_server.add_tool(list_supported_cities)

if __name__ == "__main__":
    weather_server.run()
```

MCP 服务器还可以发布到 [Smithery](https://smithery.ai/) 平台（类似 PyPI / npm），供全球开发者使用。发布需要准备 `smithery.yaml`、`pyproject.toml` 和 `Dockerfile` 等标准配置文件。

## 三、A2A（Agent-to-Agent Protocol）

### 3.1 设计理念

A2A 由 Google 提出，核心设计理念是**实现智能体之间的点对点通信**。与 MCP 关注"智能体与工具"不同，A2A 关注"智能体之间如何协作"。

传统的中央协调器（星型拓扑）存在三个问题：
- **单点故障**：协调器失效导致系统瘫痪
- **性能瓶颈**：所有通信经过中心节点
- **扩展困难**：增加智能体需改动中心逻辑

A2A 采用**点对点（P2P）架构**（网状拓扑），允许智能体直接通信，从根本上解决上述问题。

### 3.2 核心概念

A2A 的核心是两个抽象概念：

| 概念 | 说明 |
|------|------|
| **任务（Task）** | 智能体间的工作单元，具有完整的生命周期 |
| **工件（Artifact）** | 任务的输出产物，如文档、数据、分析结果 |

### 3.3 任务生命周期

A2A 为任务定义了标准化的生命周期状态机：

```
创建(Created) → 协商(Negotiating) → 执行中(In Progress) → 完成(Completed)
                                        ↓
                                    失败(Failed) → 重试/放弃
```

该机制使智能体可以进行**任务协商**（讨论任务范围和资源需求）、**进度跟踪**（实时了解任务执行状态）和**异常处理**（失败时自动重试或转交其他智能体）。

### 3.4 请求生命周期

A2A 的请求遵循四个主要步骤：

1. **代理发现**：找到能处理任务的智能体
2. **身份验证**：验证智能体身份
3. **发送消息 API**：同步请求/响应
4. **发送消息流 API**：流式通信

### 3.5 应用场景

A2A 适用于需要多智能体紧密协作的场景。典型案例如智能客服系统：

- **接待员 Agent**：分析客户问题类型，路由到对应专家
- **技术专家 Agent**：回答技术问题
- **销售顾问 Agent**：回答销售和价格问题

各 Agent 通过 A2A 协议直接通信，接待员将问题转发给合适的专家，专家将结果返回给接待员，形成完整的协作链。

## 四、ANP（Agent Network Protocol）

### 4.1 设计理念

ANP 是一个概念性协议框架（目前由开源社区维护，生态尚不成熟），核心设计理念是**构建大规模智能体网络的基础设施**。

- MCP 解决"如何访问工具"
- A2A 解决"如何与其他智能体对话"
- ANP 解决"如何在大规模网络中发现和连接智能体"

ANP 的设计哲学是"**去中心化服务发现**"。在包含成百上千个智能体的网络中，如何让智能体找到它需要的服务？ANP 提供服务注册、发现和路由机制，让智能体动态发现网络中的其他服务。

### 4.2 核心挑战与解决方案

| 挑战 | ANP 解决方案 |
|------|-------------|
| **服务发现** | 通过公开的发现服务，基于语义/功能描述查询定位智能体 |
| **智能路由** | 根据负载、成本等因素选择最合适的智能体 |
| **动态扩展** | 新智能体注册后即可被其他成员发现和调用 |
| **身份验证** | 基于 DID（去中心化标识符）的身份验证机制 |

### 4.3 交互流程

ANP 的完整交互流程包括三个关键步骤：

**1. 服务发现与匹配**：智能体 A 通过公开的发现服务，基于语义或功能描述查询，定位到符合需求的智能体 B。发现服务通过预先爬取各智能体对外暴露的标准端点（`.well-known/agent-descriptions`）来建立索引。

**2. 基于 DID 的身份验证**：智能体 A 使用其私钥对包含自身 DID 的请求进行签名，智能体 B 通过解析 DID 获取公钥验证签名真实性，建立可信通信。

**3. 标准化的服务执行**：身份验证通过后，双方依据预定义的标准接口和数据格式进行数据交换或服务调用。

> 🔑 ANP 的核心是利用 DID 构建去中心化的信任根基，借助标准化描述协议实现服务动态发现，使智能体无需中央协调即可安全、高效地形成协作网络。

## 五、三大协议对比与选型

### 5.1 协议对比

| 维度 | MCP | A2A | ANP |
|------|-----|-----|-----|
| **提出者** | Anthropic | Google | 开源社区 |
| **通信对象** | 智能体 ↔ 工具 | 智能体 ↔ 智能体 | 智能体网络 |
| **核心概念** | Tools / Resources / Prompts | Task / Artifact | Service Discovery / DID |
| **架构模式** | Host-Client-Server | 点对点（P2P） | 去中心化网络 |
| **设计哲学** | 上下文共享 | 对等通信 | 去中心化服务发现 |
| **适用场景** | 访问外部工具和资源 | 多智能体协作 | 大规模智能体网络 |
| **生态成熟度** | 成熟，社区丰富 | 较成熟，官方 SDK 可用 | 早期，概念性实现为主 |
| **典型用例** | 文件系统、GitHub、数据库访问 | 研究员+撰写员+编辑协作 | 分布式任务调度、负载均衡 |

### 5.2 选型指南

- **需要访问外部服务**（文件、数据库、API）→ 选择 **MCP**
- **需要多个智能体相互协作完成任务** → 选择 **A2A**
- **要构建大规模智能体生态系统** → 考虑 **ANP**
- **复杂系统** → 三者可以组合使用，MCP 负责工具层，A2A 负责协作层，ANP 负责网络层

> 🔑 当前协议生态还处于发展早期，MCP 的生态相对成熟。推荐优先选择大公司背书的工具和服务，降低维护风险。

## 面试题精选

**1. MCP 和 Function Calling 的本质区别是什么？它们是竞争关系吗？**

Function Calling 是大语言模型的内在能力，体现模型"理解何时调用函数"的智能；MCP 是基础设施协议，在工程层面解决"工具与模型如何连接"的问题。两者相辅相成——Function Calling 是技能（会打电话），MCP 是标准（电话通信协议）。MCP 的核心优势在于模型无关性和工具自动发现能力。

**2. MCP 的 Host-Client-Server 三层架构中，各层的职责分别是什么？这种设计有什么优势？**

Host 负责用户体验和对话管理（如 Claude Desktop），Client 负责与 MCP Server 的协议通信，Server 负责具体功能实现。优势是关注点分离：开发者只需关注 Server 开发，无需关心 Host 和 Client 的实现细节。每层可以独立演进和替换。

**3. A2A 协议为什么要采用点对点架构而不是中央协调器？**

中央协调器存在三个问题：单点故障（协调器失效导致系统瘫痪）、性能瓶颈（所有通信经过中心节点）、扩展困难（增加智能体需改动中心逻辑）。P2P 架构让智能体直接通信，避免了这些问题，但需要更复杂的任务协商和状态同步机制。

**4. ANP 的 DID（去中心化标识符）身份验证机制是如何工作的？**

智能体 A 使用私钥对包含自身 DID 的请求签名，智能体 B 收到后解析 DID 获取对应公钥，验证签名真实性和请求完整性。DID 作为去中心化信任根基，无需中心化的证书颁发机构，适合大规模开放网络环境。

**5. 在什么场景下需要同时使用 MCP、A2A 和 ANP 三种协议？**

典型场景如大规模智能客服系统：MCP 用于各智能体访问内部数据库、知识库等工具；A2A 用于多个专业客服智能体之间的协作和任务转交；ANP 用于在大规模并发场景下发现和路由到最合适的客服智能体，实现负载均衡。

**6. MCP 协议支持哪几种传输方式？各自适用于什么场景？**

五种：Memory（测试/原型）、Stdio（本地开发，通过标准输入输出通信，最常用）、HTTP（生产环境/远程服务）、SSE（实时通信/流式处理）、StreamableHTTP（双向流式通信）。选择依据是部署环境和通信需求——本地开发用 Stdio，远程服务用 HTTP/SSE。

**7. 如何设计一个自定义 MCP 服务器？需要考虑哪些关键要素？**

核心步骤：创建 MCPServer 实例、定义工具函数（明确输入参数和返回格式）、注册工具到服务器、运行服务器。关键要素包括：清晰的工具描述（LLM 依赖描述来决定是否使用工具）、参数的 JSON Schema 定义、错误处理和超时机制、安全认证（特别是访问私有数据时）。

**8. A2A 的任务生命周期包含哪些状态？这种设计有什么好处？**

状态包括：创建、协商、执行中、完成、失败。好处是提供了标准化的协作流程管理——协商阶段让智能体讨论任务范围和资源需求，状态跟踪让各方了解进度，失败状态支持自动重试或任务转交，使多智能体协作具有可预测性和可恢复性。
